# 1. BUSINESS REQUIREMENT

There are **10 line departments** in Phase 1.

Each department has:

* Exactly **one Department Coordinator**
* One associated **HOD**
* The Coordinator submits internal visitor requests **on behalf of the HOD**
* The HOD does **NOT** approve individual visitor requests.

The Department Coordinator is the authorized data-entry/requesting user.

The HOD is only the **represented department authority** associated with that Coordinator account.

### Important workflow rule

**Coordinator → SCR Review**

There is **NO**

**Coordinator → HOD Approval → SCR**

workflow.

Do not create an HOD approval step.

# 9. BACKEND IDENTITY ASSIGNMENT

This is a critical security requirement.

The backend must obtain the authenticated user's identity from the existing secure authentication mechanism.

When the Coordinator creates an internal visitor request, the backend must automatically determine:

```text
authenticated_user_id
        ↓
Coordinator account
        ↓
department_id
        ↓
represented_hod_id
```

The backend must assign these values itself.

For example:

```python
request.requester_id = current_user.id
request.department_id = current_user.department_id
request.hod_id = current_user.hod_id
```

Use the actual model/property names from the existing codebase rather than blindly copying these names.

---

# 10. NEVER TRUST CLIENT IDENTITY DATA

Do NOT treat client-submitted values as authoritative for:

* User ID
* Coordinator ID
* Department ID
* HOD ID
* Requesting department
* Represented HOD

Even if the frontend sends these values, the backend must ignore/reject them as authoritative identity information.

The secure source must be the authenticated user/session/token.

A malicious Coordinator must not be able to modify a request payload such as:

```json
{
  "department_id": 5,
  "hod_id": 8
}
```

to create a request for another department.

The backend must derive the correct values from the logged-in account.

---

# 11. AUTHORIZATION BOUNDARY

A `DEPARTMENT_COORDINATOR` may create internal visitor requests **only for their assigned department and represented HOD**.

For example:

```text
IT Coordinator
      ↓
IT requests only
```

The IT Coordinator must not be able to create:

```text
Finance request
HR request
Engineering request
another department's request
```

by modifying frontend fields or API payloads.

Enforce this on the backend.

Frontend restrictions alone are NOT sufficient.

# 27. FINAL EXPECTED RESULT

The final system should behave like this:

```text
                    ADMIN
                      │
                      │ creates account
                      ▼
          ┌──────────────────────────┐
          │ Department Coordinator   │
          │ Role: DEPARTMENT_        │
          │       COORDINATOR        │
          └────────────┬─────────────┘
                       │
                       │ assigned by Admin
                       ▼
              ┌─────────────────┐
              │   Department    │
              └────────┬────────┘
                       │
                       ▼
                 Represented HOD
                       │
                       │
Coordinator Login ─────┘
       │
       ▼
Coordinator Dashboard
       │
       ├── Coordinator Name [READ ONLY]
       ├── Department [READ ONLY]
       ├── Represented HOD [READ ONLY]
       │
       ▼
Internal Visitor Request Form
       │
       │ Submit
       ▼
FastAPI
       │
       ├── authenticated user
       ├── coordinator ID
       ├── department ID
       └── represented HOD ID
              ↓
        automatically assigned
              │
              ▼
        SCR Review / Visibility
              │
              ▼
     Existing Pass Workflow
```

The core principle is:

**Admin creates/configures the Coordinator account → Coordinator logs in → system automatically knows who they are, which department they represent and which HOD they represent → Coordinator submits the internal visitor request → request goes directly to the existing SCR workflow.**

HOD approval is completely removed from the internal request path.
